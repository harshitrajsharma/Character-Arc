# Prisma Migration Rules

1. **Never write raw SQL for business logic**: All data mutations (inserts, updates, deletes) must be executed using Prisma in Next.js Server Actions. Do not write new Supabase PostgreSQL Functions (RPCs) or Triggers for business logic.
2. **Use Prisma Transactions**: When performing multiple related mutations (e.g. creating a `ToolRun`, creating a `Block`, and creating a `BlockRelation`), they must be wrapped in a `prisma.$transaction` to ensure atomicity.
3. **Database Security Context**: Because we are shifting away from Row Level Security (RLS) policies within custom SQL, Server Actions MUST perform explicit authorization checks before querying or mutating data. You must verify that the user is the owner of the workspace or has the proper workspace membership role before allowing a read/write operation via Prisma.
4. **Tool Installations**: The application manages AI tools via `tool_installations`, `tool_runs`, etc. The logic for executing a tool action (e.g. `exam.create` or `arc.create`) should live in handlers defined in `lib/tools/execute-tool-action.ts` (or respective domains), and those handlers must use Prisma to write the exact same rows that the old SQL RPCs used to write.
5. **No DB Migrations for Logic**: `supabase/migrations/` should only contain SQL generated by `prisma migrate diff` for table structures. Do not add raw SQL dumps for functions.

6. **Row Level Security (RLS) Strategy**: To prevent direct REST API access via the public Supabase Anon Key while allowing Prisma to bypass RLS, we globally enable RLS on all tables without defining any policies (which defaults to 'Deny All' for public requests). If you create new tables, you should append a migration to enable RLS on them, but do NOT write custom SQL policies for them.
